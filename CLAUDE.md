## 1. О проекте

**Что это.** Веб-платформа об экологическом состоянии Гомельской области: интерактивная карта проблемных территорий, источников выбросов и ООПТ, автоматически обновляемые данные о качестве воздуха, состояние рек и канал обратной связи — жители отмечают экологические проблемы (свалка, сброс, дым, вырубка) с фото и следят за статусом обращения.

**Проблема.** Экологическая информация по региону разбросана по отчётам, PDF и сайтам ведомств, обновляется редко и не привязана к карте. У жителя нет простого способа сообщить о проблеме и увидеть, что с ней происходит.

**Решение.** Один публичный профиль региона на живых данных + гражданские обращения с модерацией и публичными статусами.

**Аудитория.**

| Кто | Зачем приходит |
|---|---|
| Жители | Узнать, чем дышат сегодня; сообщить о свалке/сбросе; следить за обращением |
| Органы власти, природоохранные службы | Сводка обращений по районам, тепловая карта, время реакции |
| Предприятия | Видеть свой вклад и динамику, публичная отчётность |
| Школы, вузы, экоактивисты | Учебные материалы, открытые данные |

## 2. Наследие прототипа

Прототип `100ideasforRB` — статический сайт (HTML/CSS/vanilla JS, Leaflet, Chart.js, localStorage). Изначально — школьный проект «Экологический профиль региона» (Брянская обл., автор — Харькова София), адаптированный под Гомель.

**Берём:**
- Концепцию и структуру разделов: карта, воздух, предприятия, вода, сравнение, калькулятор, новости, база знаний.
- Список районов (21 + г. Гомель), координаты точек как стартовый seed (после проверки).
- Тексты базы знаний (`knowledge-data.js`) — после вычитки.
- Формулы калькулятора углеродного следа (`features.js`) — после проверки коэффициентов.

**Выкидываем:**
- Все захардкоженные цифры (AQI, PM, рейтинги областей, «отчёты облисполкома») — **выдуманы**.
- Новости-заглушки со ссылками на реальные СМИ — **выдуманы**, недопустимо.
- localStorage как хранилище, «админку» с паролем `eco2026` в JS, `mailto:`-форму.
- `.vs/`, видео (~96 МБ), `~$*.odt`, PHP-роутер, неиспользуемые `config.json`/`data/*.json`.

**Авторство:** до подачи решить вопрос с исходным автором (соавторство либо полная переработка и удаление её данных из футера/форм). См. §16.

## 3. Принципы

1. **У каждой цифры есть источник и дата.** Нет источника — нет цифры. Модельные данные подписываются как модельные. Плейсхолдеры в UI помечаются явно (`[демо-данные]`), в прод не уходят.
2. **Данные живут в БД, не в коде.** Компоненты ничего не хардкодят.
3. **Mobile first по функциям, desktop first по вау.** Обращение с телефона должно отправляться за 30 секунд; главная должна впечатлять на проекторе.
4. **Производительность важнее эффектов.** Защита пройдёт на слабом ноутбуке. Lighthouse Performance ≥ 85 на главной.
5. **Простой деплой.** Один бинарник бэка + статика фронта + Caddy.

## 6. Архитектура

```
                     ┌──────────────────────────── VPS (РБ) ─────────────────────────────┐
                     │                                                                    │
 Браузер ──HTTPS──▶  │  Caddy (TLS, gzip)                                                 │
 Telegram ──────────▶│     │                                                              │
                     │     ▼                                                              │
                     │  PocketBase ── /api/*        REST + realtime (SSE)                 │
                     │     │          /_/           админка                               │
                     │     │          /*            SPA из pb_public (собранный front/)   │
                     │     │                                                              │
                     │     ├─ pb_data/  SQLite + загруженные фото + бэкапы                │
                     │     └─ pb_hooks/ cron: сбор воздуха; хуки: статусы, уведомления    │
                     │                                                                    │
                     │  tg-bot (опц.) ──▶ PocketBase API (сервисный аккаунт)               │
                     └────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                     Open-Meteo Air Quality API (раз в час)
```

- Фронт — SPA, собирается в `front/dist` и кладётся в `pb_public/`. PocketBase отдаёт и статику, и API с одного домена → нет CORS.
- Вся бизнес-логика, которой нельзя доверять клиенту (смена статусов, роли, валидации), — в API rules и `pb_hooks`.

### Контент

- **`news`** — title, slug, body (editor), tag, cover (file), published_at, source_url, is_published.
- **`articles`** — база знаний: title, slug, category, body, order, is_published.

### Пользователи

**`users`** (auth-коллекция): name, avatar, `role` select `user`/`moderator`/`admin` (default `user`, менять может только admin), telegram_id, notify_district (relation → districts), notify_aqi_threshold (number).

### API rules (основное)

| Коллекция | list/view | create | update | delete |
|---|---|---|---|---|
| districts, places, enterprises, air_*, water_readings, sources | все | admin | admin | admin |
| news, articles | `is_published = true \|\| @request.auth.role = "admin"` | admin | admin | admin |
| reports | `status != "new" && status != "rejected" \|\| author = @request.auth.id \|\| @request.auth.role ?= "moderator" \|\| @request.auth.role ?= "admin"` | `@request.auth.id != ""` | модератор/админ (статус, комментарий); автор — только описание и только пока `status = "new"` | admin |
| report_events | как у родительского report | только хук | — | — |
| users | только сам себя / admin | открыта (регистрация) | сам себя, кроме `role` | admin |

> Правила выше — намерение. Синтаксис сверить с документацией текущей версии PocketBase и покрыть тестами (запрос анонимом / юзером / модератором).

| Воздух (PM2.5, PM10, NO₂, SO₂, O₃, CO, US AQI), факт + прогноз | **Open-Meteo Air Quality API** (модель CAMS, сетка ~10–40 км) | cron раз в час | «Модельные данные CAMS / Open-Meteo» + лицензия CC BY 4.0. Бесплатно для некоммерческого использования — сверить лимиты |

**Важно:** в текущем макете стоит подпись «Источники: Белгидромет, посты мониторинга», а цифры взяты из прототипа (выдуманы). До защиты либо реальные данные с реальной подписью, либо Open-Meteo с подписью «модельные данные».

## 12. Хостинг и деплой

- **VPS в РБ**: hoster.by или CloudVPS.by; 1 vCPU / 1–2 ГБ RAM / 20+ ГБ SSD, Ubuntu 24.04. Для PocketBase хватает с запасом.
- **Домен** `.by` (тот же регистратор). Хостинг в РБ обязателен для сайтов юрлиц/ИП; для студпроекта — не обязательно, но нужен, если платформу заберёт вуз/госорган, плюс оплата белкартой.
- **docker-compose:** `caddy` (80/443, авто-TLS Let's Encrypt) + `pocketbase` (volume `pb_data`) + опционально `bot`.
- **Бэкапы:** встроенные бэкапы PocketBase по расписанию (ежедневно, хранить 7) + копия вне сервера (S3-совместимое хранилище или rsync на другой хост).
- **CI/CD (GitHub Actions):** на push в `main` → `npm ci && npm run build` → копия `front/dist` в `back/pb_public` → rsync `pb_hooks`, `pb_migrations`, `pb_public` на сервер по SSH → `docker compose up -d`. Миграции применяются автоматически при старте PocketBase.
- **Окружения:** `local` (бинарник PocketBase + `vite dev` с прокси `/api` → `:8090`), `prod`. Staging — отдельный поддомен, если успеем.
- **Мониторинг:** uptime-пинг (бесплатный внешний сервис) + алерт в Telegram, если cron воздуха не отработал > 3 часов.

## 13. Правила разработки

### Общие
- TypeScript `strict`, без `any`. Типы коллекций генерировать `pocketbase-typegen` после каждой смены схемы.
- Все запросы к API — только через хуки в `front/src/api/` (`useAirReadings`, `usePlaces`, …). Компоненты не вызывают `pb` напрямую.
- Никаких данных в компонентах. Seed — в `back/seed/*.json`, контент — через админку.
- Цвета, отступы, радиусы — только токены из §10.1 (Tailwind theme), без «магических» hex в компонентах.
- Пользовательский текст никогда не рендерится как HTML. Если нужен rich text (новости) — DOMPurify.
- Схема меняется только через админку локально → сгенерированная миграция коммитится вместе с кодом.
- Ветки: `main` (прод) ← `feat/*`; PR с коротким описанием и скриншотом для UI.
- Коммиты: `feat:`, `fix:`, `chore:`, `docs:`.

### Работа с нейронками
- Давать ассистенту этот файл + конкретный раздел, а не «сделай сайт».
- Одна задача = одна фича/компонент. Перед генерацией — указать, какие файлы трогать.
- Схема данных (§8) и API rules фиксируются в первую неделю; менять их — только осознанно, с обновлением этого файла.
- После каждой фичи — прогон: сборка без ошибок, ручной проход сценария, проверка API rules запросами от анонима/юзера/модератора.
- Не принимать сгенерированный код, который добавляет новые зависимости без причины или дублирует существующие хуки/компоненты.
- Этот файл обновлять при каждом архитектурном решении (§16 → в соответствующий раздел).
