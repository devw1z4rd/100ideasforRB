## 1. О проекте

**Что это.** Веб-платформа об экологическом состоянии Гомельской области: интерактивная карта проблемных территорий, источников выбросов и ООПТ, автоматически обновляемые данные о качестве воздуха, состояние рек и канал обратной связи — жители отмечают экологические проблемы (свалка, сброс, дым, вырубка) с фото и следят за статусом обращения.

**Проблема.** Экологическая информация по региону разбросана по отчётам, PDF и сайтам ведомств, обновляется редко и не привязана к карте. У жителя нет простого способа сообщить о проблеме и увидеть, что с ней происходит.

**Решение.** Один публичный профиль региона на живых данных + гражданские обращения с модерацией и публичными статусами.

**Аудитория.**

| Кто | Зачем приходит |
|---|---|
| Жители | Узнать, чем дышат сегодня; сообщить о свалке/сбросе; следить за обращением |
| Органы власти, природоохранные службы | Сводка обращений по районам, тепловая карта, время реакции |
| Предприятия | Видеть свой вклад и динамику, публичная отчётность |
| Школы, вузы, экоактивисты | Учебные материалы, открытые данные |

## 2. Наследие прототипа

Прототип `100ideasforRB` — статический сайт (HTML/CSS/vanilla JS, Leaflet, Chart.js, localStorage). Изначально — школьный проект «Экологический профиль региона» (Брянская обл., автор — Харькова София), адаптированный под Гомель.

**Берём:**
- Концепцию и структуру разделов: карта, воздух, предприятия, вода, сравнение, калькулятор, новости, база знаний.
- Список районов (21 + г. Гомель), координаты точек как стартовый seed (после проверки).
- Тексты базы знаний (`knowledge-data.js`) — после вычитки.
- Формулы калькулятора углеродного следа (`features.js`) — после проверки коэффициентов.

**Выкидываем:**
- Все захардкоженные цифры (AQI, PM, рейтинги областей, «отчёты облисполкома») — **выдуманы**.
- Новости-заглушки со ссылками на реальные СМИ — **выдуманы**, недопустимо.
- localStorage как хранилище, «админку» с паролем `eco2026` в JS, `mailto:`-форму.
- `.vs/`, видео (~96 МБ), `~$*.odt`, PHP-роутер, неиспользуемые `config.json`/`data/*.json`.

**Авторство:** до подачи решить вопрос с исходным автором (соавторство либо полная переработка и удаление её данных из футера/форм). См. §16.

## 3. Принципы

1. **У каждой цифры есть источник и дата.** Нет источника — нет цифры. Модельные данные подписываются как модельные. Плейсхолдеры в UI помечаются явно (`[демо-данные]`), в прод не уходят.
2. **Данные живут в БД, не в коде.** Компоненты ничего не хардкодят.
3. **Mobile first по функциям, desktop first по вау.** Обращение с телефона должно отправляться за 30 секунд; главная должна впечатлять на проекторе.
4. **Производительность важнее эффектов.** Защита пройдёт на слабом ноутбуке. Lighthouse Performance ≥ 85 на главной.
5. **Простой деплой.** Один бинарник бэка + статика фронта + Caddy.

## 6. Архитектура

```
                     ┌──────────────────────────── VPS (РБ) ─────────────────────────────┐
                     │                                                                    │
 Браузер ──HTTPS──▶  │  Caddy (TLS, gzip)                                                 │
 Telegram ──────────▶│     │                                                              │
                     │     ▼                                                              │
                     │  PocketBase ── /api/*        REST + realtime (SSE)                 │
                     │     │          /_/           админка                               │
                     │     │          /*            SPA из pb_public (собранный front/)   │
                     │     │                                                              │
                     │     ├─ pb_data/  SQLite + загруженные фото + бэкапы                │
                     │     └─ pb_hooks/ cron: сбор воздуха; хуки: статусы, уведомления    │
                     │                                                                    │
                     │  tg-bot (опц.) ──▶ PocketBase API (сервисный аккаунт)               │
                     └────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                     Open-Meteo Air Quality API (раз в час)
```

- Фронт — SPA, собирается в `front/dist` и кладётся в `pb_public/`. PocketBase отдаёт и статику, и API с одного домена → нет CORS.
- Вся бизнес-логика, которой нельзя доверять клиенту (смена статусов, роли, валидации), — в API rules и `pb_hooks`.

### Сбор воздуха (`back/pb_hooks/air.pb.js`, логика — `lib/air.js`)

- `air_fetch`, каждый час в :05 UTC: один запрос Open-Meteo по всем активным `air_points` (`past_days=1`, `forecast_days=5`, время UTC) → upsert в `air_readings` по (point, ts), `is_forecast = ts > now`. Неизменившиеся часы не пересохраняются. Час, где хоть одна переменная пришла `null`, пропускается: number-поле PocketBase не хранит null, а 0 выглядел бы как чистый воздух.
- `air_daily`, 00:20 по Минску: вчера и позавчера (местные сутки, UTC+3) → `air_daily` по фактическим часам; сутки без 18 из 24 часов не пишутся. Затем удаляются почасовые старше 90 дней.
- `pocketbase air-backfill [YYYY-MM-DD]` — разово после деплоя: история с даты (по умолчанию 90 дней) кусками по месяцу через ту же агрегацию, прогноз, `air_daily`, чистка почасовых старше 90 дней. Для периода «С начала года» на главной — `air-backfill 2026-01-01` (~1 мин).
- `AIR_API_URL` переопределяет адрес Open-Meteo (тесты, локальный прокси). Запустить cron вручную — админка → Settings → Crons.

### Уровни рек (`back/pb_hooks/rivers.pb.js`, логика — `lib/rivers.js`)

- `river_fetch`, 06:40 и 14:40 UTC (утром Белгидромет выкладывает уровни на 8:00; второй запуск — если сайт не ответил): `pogoda.by/api/v2/hydrology/hydro-markers` → посты, попавшие в районы области (по полигонам `districts.geometry`, допуск 1 км — посты на пограничном Днепре), upsert в `river_posts` по коду поста; затем `graph/<код>` по каждому посту → последние 30 дней в `river_levels`, upsert по (post, date). Каждый запуск заново проходит месяц, поэтому пропущенные дни догружаются сами.
- API не документирован (им пользуется карта «Гидро» на pogoda.by); pogoda.by рвёт соединения — запрос повторяется до 4 раз с паузой, 4xx не повторяется. Не ответил один пост — берётся его последнее значение из hydro-markers.
- `pocketbase river-fetch` — то же вручную, разово после деплоя. `RIVER_API_URL` переопределяет адрес API.

## 8. Модель данных (PocketBase)

Типы — PocketBase: `text`, `editor`, `number`, `bool`, `select`, `relation`, `file`, `date`, `json`, `url`, `geoPoint`. Если в выбранной версии нет `geoPoint` — два `number`-поля `lat`/`lon`.

**`districts`** — районы (22 записи: 21 район + г. Гомель)
| поле | тип | |
|---|---|---|
| name | text, unique | «Жлобинский» |
| name_be | text | для C4 |
| center | geoPoint | райцентр |
| area_km2, population | number | |
| forest_cover | number | % |
| geometry | json | GeoJSON-полигон района из OSM; по нему хук находит район обращения. У Гомельского района «дырки» под г. Гомель |

**`sources`** — источники данных (на них ссылаются все остальные коллекции)
| поле | тип | |
|---|---|---|
| title | text | «Open-Meteo Air Quality (CAMS)» |
| publisher | text | |
| url | url | |
| license | text | |
| accessed_at | date | |
| kind | select: `model`, `official`, `media`, `user`, `reference` | `reference` — справочные данные (границы, координаты) |

**`enterprises`** — предприятия-источники выбросов
| поле | тип | |
|---|---|---|

| поле | тип | |

| territory | text | «Гомельская область», «Республика Беларусь», «г. Минск» |
| year | number | |
| indicator | select: `generated`, `captured`, `stationary`, `mobile` | отходит от стационарных источников / уловлено и обезврежено / выбросы предприятий по веществам / выбросы транспорта |

| unit | text | |

Выбросы предприятий региона = `generated − captured` (методика Белстата; сверено: Гомельская обл. 108,2 / 95,1 / 79,9 тыс. т за 2023–2025). Данные — `back/seed/emission_stats.json`, собирает `back/seed/tools/build-emissions.mjs` из `back/seed/belstat/*.csv` (dataportal.belstat.gov.by) + транспорт по областям из буклетов Белстата.

| name | text |
| district | relation → districts |
| lat, lon | number |
| active | bool |

**`air_readings`** — почасовые значения; **уникальный индекс (point, ts)**
| поле | тип | |
|---|---|---|
| point | relation → air_points | |
| ts | date | UTC |
| pm2_5, pm10, no2, so2, o3, co | number | мкг/м³ |

### 10.4 Блок карты (тёмная панель, радиус `--radius-lg`)

**Реализовано** (`front/src/components/sections/map/`, карта — `components/map/MapView.tsx`, тексты — `content/map.ts`). Вид — по макету, наполнение — только реальными данными:

Подписи — HTML-маркеры шрифтом сайта. Ни тайлов, ни шрифтов с чужих серверов — карта работает офлайн (защита без интернета, §15). Цвета — токены `--map-*` в `tokens.css`.
- Слои-чипы: «Качество воздуха» (21 город, цвет точки — AQI сейчас), «Обращения жителей» (публичные статусы, realtime), «Реки: уровень воды» (посты Белгидромета: треугольник как на карте уровенного режима — направление растёт / без изменений / падает, цвет — к порогам поста; рисуются поверх городов, пост часто в самом городе) и «Реки: качество воды» (участки рек из квартального обзора, §10.8; по умолчанию выключен — стоит у тех же городов). «Проблемные территории» и «ООПТ» появляются, только когда в `places` есть записи с источником; предприятия — с секцией §10.7.
- Оверлей слева сверху вместо «AQI 54 по области» (среднее): «N из 21 городов с хорошим воздухом», шкала AQI 0–200 с отметкой каждого города, хуже/лучше всего, обращения в работе/устранено.
- Карточка справа (белая, `.light`) — выбранный город: AQI и показатели сейчас, «PM2.5 выше нормы ВОЗ за 30 дней», ← → по городам, «Подробнее о воздухе» (к `#air` с этим городом), «Приблизить».
- Выбранный город общий с разделом «Воздух» — в адресе `?town=`. Клик по району выбирает его город (у Гомельского района — Гомель). Если карта приближена (или город вне видимой части), при смене города она сама плавно переезжает к нему, сохраняя масштаб; на обзоре всей области не двигается.
- Легенда: точка города/обращение/ЧАЭС, чекбоксы «Реки», «Подписи городов», «Границы районов» (при приближении границы видны всегда). Снизу — масштабная линейка, атрибуция, «Вся область», зум.
- Прокрутка страницы не зумит карту (cooperative gestures, подсказка по-русски). MapLibre — ленивый чанк (~300 КБ gzip) + воркер, грузятся при подходе к карте.
- Мобила: панели — под картой, подписи городов по умолчанию выключены (кроме Гомеля и выбранного), чипы скроллятся.

### 10.6 Секция «Воздух»

Реализовано: `front/src/components/sections/air/`, расчёты — `lib/airStats.ts`, тексты и нормы — `content/air.ts`.

**Принцип:** никакого одного среднего по области — оно прячет города и дни с плохим воздухом («средняя температура по больнице»). Всегда видно: выбранный город, разброс по всем городам, сколько дней выше нормы.

- Eyebrow «Воздух», H2, lead. Справа: выбор города (список 21 города + «Рядом со мной» по геолокации — координаты остаются в браузере) и сегмент периода **7 дней / 30 дней / 90 дней / С начала года** (активный — чёрный). Периоды — завершённые минские сутки до вчера.
- **«Сейчас»:** AQI выбранного города крупно + категория словами (шкала US EPA, `lib/aqi.ts`); справа «Хуже всего сейчас» и «Лучше всего» — города кликабельны.
- **4 карточки** PM2.5 / PM10 / NO₂ / SO₂ — радиогруппа, выбранная выделена рамкой. В карточке: суточная норма ВОЗ 2021, пояснение простыми словами, крупно **«N из M дней выше нормы ВОЗ»**, «в прошлый период: K» (тот же срок сразу перед; для «с начала года» нет), худший день периода со значением и «на 49% / в 2,1 раза выше нормы». Отступление от макета: вместо «май → авг + дельта %» — дни выше нормы и худший день; цвета линий по показателям убраны — зелёный/жёлтый/красный в секции значат только уровень относительно нормы.
- **График** (Recharts, ленивый чанк — грузится при подходе к экрану): один показатель — линия выбранного города, серая полоса — разброс min–max по всем городам за сутки, пунктир — норма ВОЗ. Над графиком фраза «Гомель — самый загрязнённый город области в N из M дней». Тултип: значение города, насколько выше нормы, «по области: от X (город) до Y (город)».
- **«Где и когда было выше нормы»:** строка — город, клетка — сутки, цвет — до нормы / до 2 норм / выше 2 норм; строки — от города с наибольшим числом плохих дней. Клик по строке выбирает город; наведение на клетку и на график подсвечивает один и тот же день в обоих, строка статуса — «17 октября: выше нормы в 6 из 21 городов · Мозырь — 18,8 мкг/м³». На мобиле полоса скроллится внутри себя.
- Сноска: модельные данные CAMS / Open-Meteo (сетка ~10 км, расчёт для центра города, не замер поста), норма ВОЗ для среднесуточной концентрации, ВОЗ допускает превышение 3–4 дня в год. Методика и источники (Open-Meteo, ВОЗ) — на `/data`.
- Нормы ВОЗ 2021, суточные: PM2.5 15, PM10 45, NO₂ 25, SO₂ 40 мкг/м³ — в `content/air.ts`.
- Пока грузится новый период, прежние данные приглушены (`aria-busy`). Позже (S1/S2): прогноз пунктиром, календарь AQI.

## 12. Хостинг и деплой

- **VPS в РБ**: hoster.by или CloudVPS.by; 1 vCPU / 1–2 ГБ RAM / 20+ ГБ SSD, Ubuntu 24.04. Для PocketBase хватает с запасом.
- **Домен** `.by` (тот же регистратор). Хостинг в РБ обязателен для сайтов юрлиц/ИП; для студпроекта — не обязательно, но нужен, если платформу заберёт вуз/госорган, плюс оплата белкартой.
- **docker-compose:** `caddy` (80/443, авто-TLS Let's Encrypt) + `pocketbase` (volume `pb_data`) + опционально `bot`.
- **Бэкапы:** встроенные бэкапы PocketBase по расписанию (ежедневно, хранить 7) + копия вне сервера (S3-совместимое хранилище или rsync на другой хост).
- **CI/CD (GitHub Actions):** на push в `main` → `npm ci && npm run build` → копия `front/dist` в `back/pb_public` → rsync `pb_hooks`, `pb_migrations`, `pb_public` на сервер по SSH → `docker compose up -d`. Миграции применяются автоматически при старте PocketBase.
- **Первый запуск БД** (из `back/`, локально и после деплоя): `pocketbase migrate up` → `pocketbase seed` → `pocketbase air-backfill 2026-01-01` → `pocketbase river-fetch` (после seed: посты относятся к районам по их полигонам). Свои команды не применяют миграции сами, поэтому `migrate up` первым; `seed` идемпотентен — повторять после правки `back/seed`.
- **Окружения:** `local` (бинарник PocketBase + `vite dev` с прокси `/api` → `:8090`), `prod`. Staging — отдельный поддомен, если успеем.
- **Мониторинг:** uptime-пинг (бесплатный внешний сервис) + алерт в Telegram, если cron воздуха не отработал > 3 часов.

## 13. Правила разработки

### Общие
- TypeScript `strict`, без `any`. Типы коллекций — `npm run typegen` (из локальной `back/pb_data`) после каждой смены схемы; `src/api/pocketbase-types.ts` руками не правится.
- Все запросы к API — только через хуки в `front/src/api/` (`useLatestAir`, `usePlaces`, `useReports`, …). Компоненты не вызывают `pb` напрямую. В каждом модуле `…Query()` — `queryOptions` с fetcher'ом (их же берут тесты и лоадеры), `use…` — обёртка; ключи начинаются с имени домена (`["reports", …]`), чтобы инвалидировать целиком.
- Интеграционные тесты фронта против живого PocketBase: `PB_TEST_URL=http://127.0.0.1:8090 PB_SUPERUSER_EMAIL=… PB_SUPERUSER_PASSWORD=… npx vitest run src/api` (без `PB_TEST_URL` пропускаются).
- Никаких данных в компонентах. Seed — в `back/seed/*.json`, контент — через админку.
- Цвета, отступы, радиусы — только токены из §10.1 (Tailwind theme), без «магических» hex в компонентах.
- Пользовательский текст никогда не рендерится как HTML. Если нужен rich text (новости) — DOMPurify.
- Схема меняется только через админку локально → сгенерированная миграция коммитится вместе с кодом.
- Ветки: `main` (прод) ← `feat/*`; PR с коротким описанием и скриншотом для UI.
- Коммиты: `feat:`, `fix:`, `chore:`, `docs:`.

### Работа с нейронками
- Давать ассистенту этот файл + конкретный раздел, а не «сделай сайт».
- Одна задача = одна фича/компонент. Перед генерацией — указать, какие файлы трогать.
- Схема данных (§8) и API rules фиксируются в первую неделю; менять их — только осознанно, с обновлением этого файла.
- После каждой фичи — прогон: сборка без ошибок, ручной проход сценария, проверка API rules запросами от анонима/юзера/модератора.
- Не принимать сгенерированный код, который добавляет новые зависимости без причины или дублирует существующие хуки/компоненты.
- Этот файл обновлять при каждом архитектурном решении (§16 → в соответствующий раздел).
