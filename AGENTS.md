## 1. О проекте

**Что это.** Веб-платформа об экологическом состоянии Гомельской области: интерактивная карта проблемных территорий, источников выбросов и ООПТ, автоматически обновляемые данные о качестве воздуха, состояние рек и канал обратной связи — жители отмечают экологические проблемы (свалка, сброс, дым, вырубка) с фото и следят за статусом обращения.

**Проблема.** Экологическая информация по региону разбросана по отчётам, PDF и сайтам ведомств, обновляется редко и не привязана к карте. У жителя нет простого способа сообщить о проблеме и увидеть, что с ней происходит.

**Решение.** Один публичный профиль региона на живых данных + гражданские обращения с модерацией и публичными статусами.

**Аудитория.**

| Кто | Зачем приходит |
|---|---|
| Жители | Узнать, чем дышат сегодня; сообщить о свалке/сбросе; следить за обращением |
| Органы власти, природоохранные службы | Сводка обращений по районам, тепловая карта, время реакции |
| Предприятия | Видеть свой вклад и динамику, публичная отчётность |
| Школы, вузы, экоактивисты | Учебные материалы, открытые данные |

## 2. Наследие прототипа

Прототип `100ideasforRB` — статический сайт (HTML/CSS/vanilla JS, Leaflet, Chart.js, localStorage). Изначально — школьный проект «Экологический профиль региона» (Брянская обл., автор — Харькова София), адаптированный под Гомель.

**Берём:**
- Концепцию и структуру разделов: карта, воздух, предприятия, вода, сравнение, калькулятор, новости, база знаний.
- Список районов (21 + г. Гомель), координаты точек как стартовый seed (после проверки).
- Тексты базы знаний (`knowledge-data.js`) — после вычитки.
- Формулы калькулятора углеродного следа (`features.js`) — после проверки коэффициентов.

**Выкидываем:**
- Все захардкоженные цифры (AQI, PM, рейтинги областей, «отчёты облисполкома») — **выдуманы**.
- Новости-заглушки со ссылками на реальные СМИ — **выдуманы**, недопустимо.
- localStorage как хранилище, «админку» с паролем `eco2026` в JS, `mailto:`-форму.
- `.vs/`, видео (~96 МБ), `~$*.odt`, PHP-роутер, неиспользуемые `config.json`/`data/*.json`.

**Авторство:** до подачи решить вопрос с исходным автором (соавторство либо полная переработка и удаление её данных из футера/форм). См. §16.

## 3. Принципы

1. **У каждой цифры есть источник и дата.** Нет источника — нет цифры. Модельные данные подписываются как модельные. Плейсхолдеры в UI помечаются явно (`[демо-данные]`), в прод не уходят.
2. **Данные живут в БД, не в коде.** Компоненты ничего не хардкодят.
3. **Mobile first по функциям, desktop first по вау.** Обращение с телефона должно отправляться за 30 секунд; главная должна впечатлять на проекторе.
4. **Производительность важнее эффектов.** Защита пройдёт на слабом ноутбуке. Lighthouse Performance ≥ 85 на главной.
5. **Простой деплой.** Один бинарник бэка + статика фронта + Caddy.

## 6. Архитектура

```
                     ┌──────────────────────────── VPS (РБ) ─────────────────────────────┐
                     │                                                                    │
 Браузер ──HTTPS──▶  │  Caddy (TLS, gzip)                                                 │
 Telegram ──────────▶│     │                                                              │
                     │     ▼                                                              │
                     │  PocketBase ── /api/*        REST + realtime (SSE)                 │
                     │     │          /_/           админка                               │
                     │     │          /*            SPA из pb_public (собранный front/)   │
                     │     │                                                              │
                     │     ├─ pb_data/  SQLite + загруженные фото + бэкапы                │
                     │     └─ pb_hooks/ cron: сбор воздуха; хуки: статусы, уведомления    │
                     │                                                                    │
                     │  tg-bot (опц.) ──▶ PocketBase API (сервисный аккаунт)               │
                     └────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                     Open-Meteo Air Quality API (раз в час)
```

- Фронт — SPA, собирается в `front/dist` и кладётся в `pb_public/`. PocketBase отдаёт и статику, и API с одного домена → нет CORS.
- Вся бизнес-логика, которой нельзя доверять клиенту (смена статусов, роли, валидации), — в API rules и `pb_hooks`.

### Загрузка главной на медленной сети

Замеры 16.11 (прод-сборка, сжатие как в `Caddyfile`, троттлинг Chrome, холодный кэш), первый экран / интерфейс / карта: Fast 4G — 0,2 / 1,0 / 1,7 с; Slow 4G — 0,6 / 3,1 / 6,9 с (до оптимизаций 3,2 / 3,2 / ~11 с); 3G — 2,1 / 10,7 / 24 с, область с городами (карта-заглушка) — на 14-й секунде. До интерфейса — ~240 КБ, до карты — ~860 КБ (MapLibre с воркером — 360 КБ, шрифты — 127 КБ): дальше упирается в ширину канала. Повторный визит — код с диска (service worker).

- **Заглушка в `index.html`**: шапка и тёмная панель карты (панель — только на `/`, атрибут `data-home`) рисуются из HTML до загрузки JS; размеры и цвета повторяют `SiteHeader` и `MapSection` — при их правке обновлять (шапка заглушки — тот же контейнер 1600 px по центру: без него на широком экране логотип прыгал на сотни пикселей). У `html` — `scrollbar-gutter: stable` (в заглушке и в `index.css`): длинная страница с React давала полосу прокрутки и сдвигала шапку; лишний отступ, который блокировка прокрутки Radix добавляет `body`, обнулён там же. Стили в сборке переносятся из `<head>` в конец `<body>` (плагин `stylesAfterShell` в `vite.config.ts`), иначе CSS блокировал бы заглушку; React стартует после загрузки стилей (`main.tsx`).
- **Данные первого экрана — одним запросом из HTML**: `GET /api/eco/home` (`back/pb_hooks/home.pb.js`) отдаёт точки воздуха, полигоны районов, значения «сейчас», суточные за 30 дней, посты и уровни рек, обзоры воды — те же строки и поля, что обычные запросы коллекций. Запрос уходит из `index.html` (`window.__ecoHome`), пока качается JS. На фронте `takeHome()` (`src/api/home.ts`): queryFn в `air.ts`, `reference.ts`, `rivers.ts`, `water.ts` сначала берут свою часть оттуда (один раз, в первую минуту после загрузки; окно суточных сверяется), иначе идут в коллекцию — маршрут не ответил, не главная, повторный запрос. **Поменялись поля или окно в этих queryFn — поменять и в `home.pb.js`.** Обращения и места — по-прежнему своими запросами (нужны права и expand).
- **Код карты качается сразу** — с первой строки `main.tsx`, одновременно с данными (`components/map/loadMapView.ts`): чанк MapView и воркер MapLibre — параллельно (воркер — `fetch` в HTTP-кэш). Окно поста уровня (`RiverPostDialog`) — отдельный чанк по первому открытию.
- **Карта-заглушка на SVG** (`sections/map/MapPreview.tsx`): данные пришли, а код карты не загрузился за 1,5 с (`SLOW_NETWORK_MS`) — в панели рисуются районы, контур области и города цветом AQI, тем же кадром, что даст MapLibre (Меркатор, `text.bounds`, отступы под панели, ограничения `MIN_ZOOM` и `maxBounds` — при их правке в `MapView` обновить и здесь). Панели с цифрами появляются тогда же. Настоящая карта в этом случае приходит без сцены старта (`skipIntro`) и проявляется поверх заглушки. На Fast 4G и быстрее код успевает, заглушки нет, сцена старта остаётся.
- **Разделы ниже карты** («Воздух», «Вода», «Предприятия») — отдельные чанки (`HomePage.tsx`): грузятся после кода карты, при первой прокрутке или сразу, если в адресе якорь; до этого — `SectionPlaceholder` той же оболочки с якорем. Модули кэшируются на сессию (возврат на главную — без заглушек); после догрузки прокрутка к якорю повторяется. Главный чанк 126 → 58 КБ gzip.
- **Service worker** (`front/sw/sw.js`, собирает плагин `serviceWorker` в `vite.config.ts`: дописывает версию и список файлов; регистрация — `lib/serviceWorker.ts`, только в сборке, после загрузки страницы и кода карты, не при Save-Data). При установке кэширует весь JS и CSS, шрифты, слои карты и страницу (то, что уже скачано, берёт из HTTP-кэша). Дальше: `/assets/*` — из кэша; страница — из сети, а если сеть не ответила за 3 с — из кэша; `/geo/*` — из кэша с обновлением на следующий раз; открытые данные API (списки коллекций, `/api/eco/home`, только запросы без входа) — из сети, кэш — когда сети нет. Итог: повторный визит не качает код, а без интернета сайт открывается с последними загруженными данными (проверено: главная целиком при остановленном сервере). Новая сборка — новый worker: страница свежая сразу (она из сети), старый кэш удаляется. Админка `/_/`, realtime, файлы и запросы с токеном идут мимо. В dev worker не ставится; `vite preview` ставит его на свой порт — снять: DevTools → Application → Service workers → Unregister.
- **Сжатие**: сборка кладёт рядом с каждым текстовым файлом `.br` и `.gz` (плагин `precompress`), Caddy отдаёт их готовыми; brotli на 15–20 % меньше gzip (MapLibre 292 → 239 КБ). Ответы API Caddy сжимает на лету — сам PocketBase их не сжимает (§12).
- Проверено и не дало выигрыша: ленивый движок Motion (−5 КБ). Не сделано: обрезка латинских шрифтов до нужных символов (−60 КБ, нужен fonttools). Троттлинг Chrome не действует на запросы из service worker — повторный визит на медленной сети им не измерить.

### Сбор воздуха (`back/pb_hooks/air.pb.js`, логика — `lib/air.js`)

- `air_fetch`, каждый час в :05 UTC: один запрос Open-Meteo по всем активным `air_points` (`past_days=1`, `forecast_days=5`, время UTC) → upsert в `air_readings` по (point, ts), `is_forecast = ts > now`. Если последний фактический час старше 20 ч (сервер стоял), вместо `past_days=1` — backfill с суток этого часа, вместе с `air_daily`. Иначе — досчёт `air_daily` за вчера и позавчера, если их нет хоть у одной активной точки (`rollupMissing`): cron 00:20 пропускается, когда сервер стоит или машина спит, и вчерашний день выпадал из графиков (так было 14.11). Неизменившиеся часы не пересохраняются. Час, где хоть одна переменная пришла `null`, пропускается: number-поле PocketBase не хранит null, а 0 выглядел бы как чистый воздух.
- `air_daily`, 00:20 по Минску: вчера и позавчера (местные сутки, UTC+3) → `air_daily` по фактическим часам; сутки без 18 из 24 часов не пишутся. Затем удаляются почасовые старше 90 дней.
- `pocketbase air-backfill [YYYY-MM-DD]` — разово после деплоя: история с даты (по умолчанию 90 дней) кусками по месяцу через ту же агрегацию, прогноз, `air_daily`, чистка почасовых старше 90 дней. Для периода «С начала года» на главной — `air-backfill 2026-01-01` (~1 мин).
- `AIR_API_URL` переопределяет адрес Open-Meteo (тесты, локальный прокси). Запустить cron вручную — админка → Settings → Crons.

### Уровни рек (`back/pb_hooks/rivers.pb.js`, логика — `lib/rivers.js`)

- `river_fetch`, 06:40 и 14:40 UTC (утром Белгидромет выкладывает уровни на 8:00; второй запуск — если сайт не ответил): `pogoda.by/api/v2/hydrology/hydro-markers` → посты, попавшие в районы области (по полигонам `districts.geometry`, допуск 1 км — посты на пограничном Днепре), upsert в `river_posts` по коду поста; затем `graph/<код>` по каждому посту → последние 30 дней в `river_levels`, upsert по (post, date). Каждый запуск заново проходит месяц, поэтому пропущенные дни догружаются сами.
- API не документирован (им пользуется карта «Гидро» на pogoda.by); pogoda.by рвёт соединения — запрос повторяется до 4 раз с паузой, 4xx не повторяется. Не ответил один пост — берётся его последнее значение из hydro-markers.
- `pocketbase river-fetch` — то же вручную, разово после деплоя. `RIVER_API_URL` переопределяет адрес API.

### Новости (`back/pb_hooks/news.pb.js`, логика — `lib/hydroNews.js`)

- `hydro_news`, 09:15 и 15:15 UTC: страница «Информация гидролога» belgidromet.by (на ней 3 последних обзора) → каждый новый обзор (по `source_url`) разбирается регулярками: дата `inner-date`, заголовок `h2`, текст до «При использовании информации…» → `news` (рубрика «Реки», абзацы как `<p>`, обложка — карта уровенного режима из `/uploads/`, `published_at` — день обзора). Уже загруженные не трогаются — правки в админке остаются.
- `pocketbase hydro-news` — то же вручную; `pocketbase hydro-news <url> …` — конкретные обзоры (архив за сезон). `BELGIDROMET_URL` переопределяет адрес.
- Хук: опубликованная новость без `published_at` получает текущее время — иначе уйдёт в конец ленты.

### Догон после простоя (`back/pb_hooks/catchup.pb.js`)

- Cron PocketBase пропущенные запуски не повторяет. Задача `catch_up` срабатывает на первой минуте после старта `serve`, снимает себя с расписания и один раз проходит: воздух (`fetchLatest` — с последнего фактического часа), реки (если нет уровня на последние 8:00), новости (страница «Информация гидролога»). Результат — в логах (`catch_up`).
- На странице Белгидромета только 3 последних обзора: если сервер стоял дольше, пропущенные — `pocketbase hydro-news <url> …`.

### API rules (основное)

| Коллекция | list/view | create | update | delete |
|---|---|---|---|---|
| districts, places, enterprises, air_*, water_readings, river_posts, river_levels, sources, emission_stats | все | admin | admin | admin |
| news, articles | `is_published = true \|\| @request.auth.role = "admin"` | admin | admin | admin |
| reports | `status != "new" && status != "rejected" \|\| (@request.auth.id != "" && author = @request.auth.id) \|\| модератор/админ` | все (вход по желанию; гостю — 10 за 10 мин с IP) | модератор/админ (статус, комментарий); автор — только описание и только пока `status = "new"` | admin |
| report_events | как у родительского report | только хук | — | — |
| users | только сам себя / admin | открыта (регистрация) | сам себя, кроме `role` | admin |

Район обращения — полигон `districts.geometry`, в который попала точка; точка вне всех полигонов отклоняется как вне области. `telegram_id` пользователь сам не задаёт — привязывает бот (S5).

- Приближение: двойной щелчок по карте — плавно к этой точке на два уровня (Shift — отдалить), двойной щелчок по городу — сразу до масштаба улиц (12); колесо с Ctrl — вдвое быстрее, чем у MapLibre по умолчанию. Кнопки «+ / −» — по уровню, в подсказке к ним — про двойной щелчок.

Окно следует теме сайта; фокус при открытии — на окне, при закрытии на маркер не возвращается (иначе всплыла бы его подсказка).

- **Старт карты — сцена-визитка** (`components/map/intro.ts`, такты `stage` 0–4 в `MapView`): пока грузится MapLibre — тёмный фон самой карты (`--map-bg`). Когда первый кадр нарисован (`idle`, не позже 1,5 с после `load`), проявляется только Беларусь ровно сверху — контур страны и границы её областей (на обзоре — светлее и толще, к посадке — как обычно); линии соседних стран (их области, граница Россия — Украина; в borders.geojson без пометки `blr`) проявляются к посадке; ограничения по области и масштабу на время сцены сняты; по краю Гомельской области рисуется граница — сплошной белой линией (`line-gradient` по `line-progress`, источник с `lineMetrics`), а сама область подсвечивается оттенком рек — видно, куда летим. Затем пролёт MapLibre `flyTo` (с подъёмом и снижением, 2,2 с) с обзора страны на область; по пути реки текут от истока к устью тем же приёмом, подсветка остывает до обычной заливки. Дальше проступают районы, нарисованная граница гаснет под привычным пунктиром; города «выстреливают» пружинкой волной от Гомеля, у каждого — кольцо-пинг цвета AQI (`.map-pop`, `.map-ping` в `index.css`; анимации стартуют с монтированием маркеров); следом посты, участки рек, подписи. Затем панели заезжают пружиной (Motion): левые — слева, карточка города — справа (на телефоне — снизу); «21 из 21» отсчитывается от нуля (`components/CountUp.tsx`), отметки городов разъезжаются по шкале AQI. Около 4,4 с сцена закончилась: градиенты сняты, ограничения камеры вернулись. Пролёт летит к тому кадру, который карта показала при загрузке с учётом `maxBounds` (а не к «чистому» `cameraForBounds`), и в конце область не вписывается заново — иначе, когда возвращалось ограничение, карта заметно сдвигалась вбок. До начала «рисования» линия полностью прозрачна (иначе у начала каждой реки виднелась точка). (Первый вариант — наклонённая 3D-камера — начинался со стороны Украины и был отвергнут.) **Производительность** (на батарее и в тихом режиме сцена рвалась; замер — прод-сборка, CPU ×2, экран ×2: кадр пролёта 39–56 → 16–18 мс, такт 3 — 292 → 134 мс): (1) градиент «рисования» — только `interpolate`, не `step`: для `step` MapLibre строит текстуру градиента шириной до 4096+ px на каждую линию каждого тайла и пересчитывает её на каждом обновлении — это и было главной нагрузкой; градиенты обновляются не чаще ~30 раз в секунду; (2) HTML-маркеры (~60) монтируются только после пролёта — MapLibre двигает каждый маркер на каждом кадре движения, даже скрытый, — и двумя волнами: такт 3 — города, через 120 мс — остальное с задержкой анимаций на столько же меньше (ритм тот же). Наложение групп задано `z-index` (подписи < места < участки рек < посты < города < обращения), контейнер холста — `isolation: isolate`; (3) маркеры — в `useMemo`, `MapView` — под `memo`, `shown` и `onReady` в `MapSection` стабильны: такты сцены, наведение и заезд панелей не перерисовывают ~60 маркеров; (4) линейка масштаба (`ScaleBar`) сама слушает движение карты — раньше масштаб жил в состоянии `MapView` и вся карта перерисовывалась React на каждом кадре; (5) панели — без filter: blur; у секции карты нет общего проявления оболочки. Облегчённый режим включается сам: если первые 10 кадров в среднем дольше 24 мс, холст на время сцены рендерится в разрешении ×0,75 от экрана (`setPixelRatio`), анимация та же; полное разрешение возвращается в 5,6 с, когда панели уже доехали (пересоздание холста — тяжёлый кадр). В dev-режиме (StrictMode, dev-React) сцена заметно тяжелее — плавность проверять на `npm run build && npm run preview`. Посреди пролёта остаются 2–3 кадра подгрузки тайлов масштаба 6; прогрев итогового плана перед сценой их не убирает (проверено). Если карта не поднялась (нет WebGL), панели появляются через 9 с. При reduced motion — сразу итоговый кадр.

- **Телефон (< 768 px, переделано 16.11):** карта квадратная, по ширине экрана (`h-[100vw]`, не выше экрана) — область видна целиком; в панели на весь экран MapLibre из-за `maxBounds` показывал её крупнее и обрезал по бокам. На обзоре видны только города: посты, участки рек, места и обращения (маркеры с классом `map-extra`) появляются с масштаба 6,3 — `MapView` ставит на корень атрибут `data-far` при переходе порога (без состояния React), правило — в `index.css`; под картой — подсказка «Приблизьте карту…». На мобиле AQI сверху, карточки 2×2. **AQI**: значение за последний час крупно с плашкой категории (`data-aqi-surface`, шкала US EPA, `lib/aqi.ts`) и время; под ним — шкала AQI 0–200 цветами категорий (как на карте): чёрная черта — сейчас, светлая скобка — в каких пределах был AQI за период по худшему часу суток (`aqiRange` по `air_daily.aqi_max`), подпись «за 30 дн. — от 27 до 80» и ⓘ: AQI — американская шкала, строже нормы ВОЗ и берёт худший час, поэтому «умеренный» AQI бывает и в дни в пределах нормы ВОЗ. Раньше здесь была полоса дней по категориям AQI («умеренный — 17 дн.») — рядом с «0 дней выше нормы ВОЗ» она читалась как противоречие. «Хуже / лучше всего сейчас» по области здесь нет — это показывает оверлей карты.
- Карточки **PM2.5 / PM10 / NO₂ / SO₂** — радиогруппа: выбранная — серой рамкой 2 px и лёгкой подложкой (чёрная резала глаз), остальные — тонкой светлой, наведение — рамка темнее и бледная подложка. В карточке: норма ВОЗ 2021 (суточная), крупно **сколько дней периода выше нормы** «из M дн.», полоса состава дней (в норме — бледно, до 2 норм, выше 2 норм — `daysHigh` в `summarizeByPoint`), худший день со значением и «на 49% / в 2,1 раза выше нормы», «в прошлый период — K» (тот же срок сразу перед; для «с начала года» нет). Пояснение выбранного показателя простыми словами — одной строкой под карточками. Полосы проявляются слева направо (CSS `summary-bar`). Отступление от макета: вместо «май → авг + дельта %» — дни выше нормы и худший день; зелёный/жёлтый/красный в секции значат только уровень относительно нормы.
- **График** (свой SVG в духе графика уровня воды, `AirChart.tsx`, ленивый чанк; Recharts больше не используется): линия выбранного города — плавная монотонная кривая (`lib/chartPath.ts`) с мягкой заливкой, серая полоса — разброс min–max по всем городам за сутки, пунктир — суточная норма ВОЗ и «2 нормы»; зоны выше нормы и выше двух норм подкрашены, а участки линии в них — цветом уровня, поэтому плохие дни видны сразу; «макс.» на линии. **Сегодня** — отдельной незавершённой точкой справа от вчера (`todayPoint` в `lib/airStats.ts`, данные — `airTodayQuery`: фактические часы всех городов с начала минских суток): пунктир от вчера и пустой кружок, он и пульсирует; в легенде «сегодня — сутки ещё идут», в подсказке «Сегодня, за N ч из 24», значение, разброс по области и что сутки не закончились — в подсчёт дней выше нормы не входит. Появление: полоса и зоны проявляются, заливка поднимается, линия прорисовывается (CSS `river-*`); при смене города, показателя или периода — заново. Ось дат — начала месяцев для длинного периода. Над графиком фраза «Гомель — самый загрязнённый город области в N из M дней». Наведение — вертикаль, точка и тёмная подсказка едут за курсором: значение, насколько выше нормы, «по области: от X (город) до Y (город)». Если история загружена не с начала периода, график и таблица начинаются с первых суток с данными, в легенде — «данные с …».
- **«Где и когда было выше нормы»** (`TownStrip.tsx`): строка — город, клетка — сутки (до 92 дней) или неделя с понедельника (дольше — «с начала года»: иначе клетки по 2 px и месиво), цвет — худшие сутки клетки: в норме (бледный зелёный, чтобы выделялись плохие) / до 2 норм / выше 2 норм; над длинным периодом — подписи месяцев. Клетки — одна SVG-сетка, нарисованная один раз (наведение двигает только подсветку столбца — год не тормозит). Строки — от города с наибольшим числом плохих дней; клик по строке выбирает город. Наведение на график и на таблицу подсвечивает те же сутки или неделю в обоих (неделя на графике — полосой), строка статуса — «17 октября: выше нормы в 6 из 21 городов · Мозырь — 18,8 мкг/м³» или «Неделя 2–8 нояб.: хотя бы одни сутки выше нормы в 6 из 21 городов · Мозырь — 2 из 7 сут., макс. 19,0».
- Сноска: модельные данные CAMS / Open-Meteo (сетка ~10 км, расчёт для центра города, не замер поста), норма ВОЗ для среднесуточной концентрации, ВОЗ допускает превышение 3–4 дня в год. Методика и источники (Open-Meteo, ВОЗ) — на `/data`.
- Нормы ВОЗ 2021, суточные: PM2.5 15, PM10 45, NO₂ 25, SO₂ 40 мкг/м³ — в `content/air.ts`.

### 10.14 Сравнение районов

**Реализовано** (`front/src/pages/ComparePage.tsx`, `components/compare/`; расчёты — `lib/compare.ts`, геометрия — `lib/geo.ts`; тексты — `content/compare.ts`). Ленивый чанк маршрута, ~7 КБ gzip. Только данные, которые уже есть на сайте; площадь, население и лесистость районов (`districts.area_km2`, `population`, `forest_cover`) не заполнены — не показываются.
- **Единица — 22 территории:** 21 район и г. Гомель. Воздух района — точка Open-Meteo в его райцентре; у Гомельского района отдельной точки нет, он получает значения Гомеля (`districtPoints`) — так и подписано.
- **«Районы по одному показателю»:** чипы PM2.5 / PM10 / NO₂ / SO₂ (дней выше суточной нормы ВОЗ за период) и «Обращения жителей» (опубликованные за период — принятые, переданные, устранённые; район — по полигону). Вывод словами («Чаще всего PM2.5 выше нормы ВОЗ — …: 10 дн. из 90. Реже всего — …»), затем картограмма и список.
- **Картограмма** — свой SVG из `districts.geometry` (равнопромежуточная проекция с cos φ, вершины ближе 1 единицы viewBox отброшены), без MapLibre: лёгкая и офлайн. Цвет — одна последовательная шкала от бледного до `--destructive`; серый — нет данных; кружки — райцентры, для которых считается воздух. Контуры и подписи — два сравниваемых района.
- **Список** — от большего к меньшему, равные делят место (1, 2, 2, 4) и идут по алфавиту. Наведение связывает строку и район на карте; клик по строке или району ставит его вторым в сравнение.
- **«Два района рядом»:** выбор первого (+ «Мой район» по геолокации — точка в полигон, координаты остаются в браузере) и второго, «поменять местами»; панель выбора липкая. Группы: воздух (AQI сейчас; дни выше нормы ВОЗ по 4 показателям — зеркальные бары от центра, дорожка — весь период, плюс худший день), реки (посты Белгидромета в районе: статус к порогам поста, уровень, дни ниже судоходного), качество воды (участки из последнего квартального обзора, попавшие в полигон района, худшее отклонение), обращения.
- Цвета районов — токены `--compare-a` (графитовый, первый) и `--compare-b` (синий, второй): одни и те же на карте, в списке и в барах.
- **Состояние — в адресе:** `?m=no2&p=ytd&a=Мозырский&b=Лельчицкий` (районы по названию, как `?town=`). Периоды — 30 / 90 дней / с начала года (7 дней убраны: почти у всех 0–1 день). По умолчанию — PM2.5 за 90 дней, г. Гомель и Мозырский.
- **Сводного индекса нет** — внизу страницы объяснено почему: показатели в разных единицах, веса были бы произволом. Источники — на `/data` (воздух и вода помечены «сравнение районов», границы OSM — отдельной строкой).

### 10.11 Анимации (умеренно)

- Появление секций при скролле — fade + 8–12 px сдвиг (Motion), один раз.
- **Анимации — когда блок показался на экране, а не при загрузке страницы** (иначе они отыгрывали за экраном и к приходу в раздел всё уже стояло; заметны были только «Предприятия»). CSS-анимации появления внутри `components/PlayInView.tsx` стоят на первом кадре (`[data-play="wait"]` в `index.css` ставит их на паузу), пока блок не виден на четверть, затем играют с начала: в «Воздухе» — сводка, график, «Прогноз», «По часам». Мини-графики уровней в «Воде» рисуются (анимация bklit), когда график виден на 60 %, точка «сейчас» — следом; карточки постов появляются волной по строке, книжки встают на полку по очереди (`whileInView`). У «Предприятий» второй ряд (регионы, вещества) — свой момент роста баров. Срабатывает один раз; при reduced motion — сразу.
- Цифры KPI — NumberFlow.
- Бары предприятий растут от 0 при появлении.
- Карта: плавный `flyTo`, пульсация выбранного маркера.
- Уважать `prefers-reduced-motion`.
- **Ноутбук от батареи** (процессор в экономном режиме, встроенная графика; замер 16.11 — Chrome, CPU ×4): (1) никаких анимаций в главном потоке, которые запускаются прокруткой, — каждый их кадр заставляет браузер пройти всю длинную страницу. Подложка активного пункта в шапке анимирует только `translate` (ширина и цвет пунктов меняются сразу): срывов кадров за проход страницы было 24, без переходов шапки — 10–14; (2) без `backdrop-blur` поверх карты и на липких панелях — размытие пересчитывается на каждом кадре движения карты и прокрутки (панели карты — `bg-background/95`, панель «Воздуха» — сплошной фон); под окнами (книжка, окно поста) размытие оставлено; (3) состояние, которое меняется при прокрутке, не должно перерисовывать раздел: `useStuck` отдаёт ref, а не state.

## 12. Хостинг и деплой

- **VPS в РБ**: hoster.by или CloudVPS.by; 1 vCPU / 1–2 ГБ RAM / 20+ ГБ SSD, Ubuntu 24.04. Для PocketBase хватает с запасом.
- **Домен** `.by` (тот же регистратор). Хостинг в РБ обязателен для сайтов юрлиц/ИП; для студпроекта — не обязательно, но нужен, если платформу заберёт вуз/госорган, плюс оплата белкартой.
- **docker-compose:** `caddy` (80/443, авто-TLS Let's Encrypt) + `pocketbase` (volume `pb_data`) + опционально `bot`.
- **Caddy — `Caddyfile` в корне** (§6 «Загрузка главной»): фронт (`front/dist` со своими `.br` / `.gz`) Caddy отдаёт сам — `file_server { precompressed br gzip }`, `/assets/*` — `Cache-Control: immutable`, остальное (страница, `sw.js`, `/geo`) — `no-cache`, неизвестный адрес — `index.html`; `/api/*` и `/_/*` — в PocketBase с `encode zstd gzip`. Переменные: `SITE_ADDRESS`, `PB_UPSTREAM`, `SITE_ROOT`. **Проверен локально 19.11 на Caddy 2.11.9** (`caddy validate`, `caddy fmt`, прогон перед PocketBase): `.br` / `.gz` отдаются по `Accept-Encoding`, `/assets/*` — immutable, страница / `sw.js` / `/geo` — no-cache, SPA-фолбэк, API сжимается (`/api/eco/home` 338 → 73 КБ gzip, 68 КБ zstd), realtime (SSE) через сжатие приходит сразу, поддельный `X-Forwarded-For` Caddy затирает. Исправлено: несуществующий `/assets/*` отдавал `index.html` с immutable на год (после деплоя открытая вкладка просит старые чанки) — теперь 404, а фронт на `vite:preloadError` перезагружается туда, куда шёл переход (`lib/staleChunks.ts`; не чаще раза в минуту — при сломанном деплое страница ошибки, а не цикл); `.geojson` шёл без Content-Type. На сервере всё равно повторить: `caddy validate`, затем `curl -sI -H "Accept-Encoding: br" https://<домен>/assets/<файл>.js` → `content-encoding: br` и `curl -sI -H "Accept-Encoding: gzip" https://<домен>/api/eco/home` → `content-encoding: gzip`. Если статику оставить за PocketBase (`pb_public`), сайт работает, но без brotli и без кэша `/assets`.
- **Trusted proxy** ставит миграция `1795039674_settings_proxy_backups.js`: заголовок `X-Forwarded-For` — иначе PocketBase видит у всех гостей IP Caddy, и лимиты по IP (10 анонимных обращений за 10 минут, 300 запросов к `/api/` за 10 с) становятся общими на весь сайт. Поэтому PocketBase слушает только `127.0.0.1`: доступный снаружи, он поверил бы заголовку от клиента (проверено: напрямую подделка проходит, через Caddy — нет). Если статику отдаёт сам PocketBase (`pb_public`, без Caddy) — заголовок в админке убрать.
- **Бэкапы:** та же миграция — ежедневно в 02:30 по Минску, хранить 7 (`pb_data/backups`). Копия вне сервера (S3-совместимое хранилище или rsync на другой хост) — вручную.
- **CI/CD (GitHub Actions):** на push в `main` → `npm ci && npm run build` → копия `front/dist` в `back/pb_public` (он же `SITE_ROOT` для Caddy) → rsync `pb_hooks`, `pb_migrations`, `pb_public` на сервер по SSH → `docker compose up -d`. Миграции применяются автоматически при старте PocketBase.
- **Первый запуск БД** (из `back/`, локально и после деплоя): `pocketbase migrate up` → `pocketbase seed` → `pocketbase air-backfill 2026-01-01` → `pocketbase river-fetch` (после seed: посты относятся к районам по их полигонам) → `pocketbase hydro-news`. Свои команды не применяют миграции сами, поэтому `migrate up` первым; `seed` идемпотентен — повторять после правки `back/seed`.
- **Окружения:** `local` (бинарник PocketBase + `vite dev` с прокси `/api` → `:8090`), `prod`. Staging — отдельный поддомен, если успеем.
- **Мониторинг:** `GET /api/eco/health` (`back/pb_hooks/health.pb.js`) — последний фактический час воздуха и последний уровень рек с возрастом; 503, если воздух старше 3 ч или уровни старше 48 ч. Внешний uptime-сервис проверяет его и шлёт алерт в Telegram на любой не-2xx — настроить при деплое.

## 13. Правила разработки

### Общие
- TypeScript `strict`, без `any`. Типы коллекций — `npm run typegen` (из локальной `back/pb_data`) после каждой смены схемы; `src/api/pocketbase-types.ts` руками не правится.
- Все запросы к API — только через хуки в `front/src/api/` (`useLatestAir`, `usePlaces`, `useReports`, …). Компоненты не вызывают `pb` напрямую. В каждом модуле `…Query()` — `queryOptions` с fetcher'ом (их же берут тесты и лоадеры), `use…` — обёртка; ключи начинаются с имени домена (`["reports", …]`), чтобы инвалидировать целиком.
- Интеграционные тесты фронта против живого PocketBase: `PB_TEST_URL=http://127.0.0.1:8090 PB_SUPERUSER_EMAIL=… PB_SUPERUSER_PASSWORD=… npx vitest run src/api` (без `PB_TEST_URL` пропускаются).
- Никаких данных в компонентах. Seed — в `back/seed/*.json`, контент — через админку.
- Цвета, отступы, радиусы — только токены из §10.1 (Tailwind theme), без «магических» hex в компонентах.
- Подсказки — только через `components/ui/tooltip.tsx`, не атрибутом `title`: с мышью — своя тёмная плашка (Radix Tooltip, наведение и фокус), на телефоне обёртка сама ставит нативный `title`.
- Пользовательский текст никогда не рендерится как HTML. Если нужен rich text (новости) — DOMPurify.
- Комментарии в коде — только на английском и только там, где без них не понять «почему»: обход бага библиотеки, «держать в синхроне с X», безопасность, неочевидное ради производительности. Пересказ кода и описания компонентов — не писать. Не ссылаться в коде на этот файл (`AGENTS.md §…`): он в `.gitignore`, в репозитории его нет.
- Схема меняется только через админку локально → сгенерированная миграция коммитится вместе с кодом.
- Ветки: `main` (прод) ← `feat/*`; PR с коротким описанием и скриншотом для UI.
- Коммиты: `feat:`, `fix:`, `chore:`, `docs:`.

### Работа с нейронками
- Давать ассистенту этот файл + конкретный раздел, а не «сделай сайт».
- Одна задача = одна фича/компонент. Перед генерацией — указать, какие файлы трогать.
- Схема данных (§8) и API rules фиксируются в первую неделю; менять их — только осознанно, с обновлением этого файла.
- После каждой фичи — прогон: сборка без ошибок, ручной проход сценария, проверка API rules запросами от анонима/юзера/модератора.
- Не принимать сгенерированный код, который добавляет новые зависимости без причины или дублирует существующие хуки/компоненты.
- Этот файл обновлять при каждом архитектурном решении (§16 → в соответствующий раздел).
